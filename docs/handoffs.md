## WEB00 Front-end test harness: unit, build check, Playwright against a lane API, a new verify command
- Run: `LANE=b JV_API_DIR=<checkout of jewelvault-api> E2E=1 npm run verify` (typecheck, changed-file lint, unit, build, build check, then Playwright); without `E2E=1` the last step is skipped by name and neither LANE nor Docker is needed. `E2E=1 npx playwright test tests/e2e/<spec>` starts and stops the lane itself (the global setup); without `E2E=1` it refuses. `npm run test:e2e` is now plain `playwright test`; the Supabase steps are out of `verify` (their scripts, `scripts/lane.mjs` and `supabase/` stay until WEB15).
- The lane (`scripts/e2e-lane.mjs`; `npm run e2e:lane -- up|down|status|ports`): the API repository's `npm run db:lane -- up <lane>` (container `jv-mariadb-<lane>`, tmpfs, no volume; an existing container is reset), the API compiled from `JV_API_DIR` into `node_modules/.cache/jv-e2e/<lane>/dist` of that checkout (not `dist/`, so two lanes never delete each other's build), an admin token made per run, then `npm run admin -- add-user` for an owner, a biller and a staff user, each signed in once and given a new password (no must-change gate). E-mails, passwords and the admin token go to `.lanes/<lane>/.env.local` (0600, git-ignored; `down` deletes it) and to `process.env`: in a spec `e2eLogin('owner' | 'biller' | 'staff')` and `e2eLane()` (`apiUrl`, `webOrigin`, `adminToken`) from `tests/e2e/global-setup.ts`. A spec that needs a must-change or deactivated user makes it itself through the admin door with that token (from the test process: the door refuses an `Origin`).
- Ports: the site on `PORT`, else the lane's (main 4028, a 4128, b 4228, c 4328), else 4028; the API on the next one (4029, 4129, 4229, 4329); `ALLOWED_ORIGINS` is exactly the site's origin and the dev server gets `NEXT_PUBLIC_API_URL` of the lane. ONE Playwright run per checkout at a time: `next dev` keeps one server per folder (the second stops with "Another next dev server is already running"); two lanes need two worktrees. Two lane STACKS at once were run (lane b and lane main in the sandbox namespace `JV_LANE_NAMESPACE=w JV_LANE_PORT_BASE=33330`, passed through to the API's lane tool): separate containers, APIs, users and ports; a Playwright run on b left main alone.
- Browser facts, proved in `tests/e2e/harness.spec.ts` (PT-W0): Chromium keeps the `Secure` cookie `__Host-jv_session` on `http://localhost`, sends it back from a page on another port of localhost (SameSite=Strict is same-site there), and the page cannot read it; a POST needs `X-JV-Client: web` and sends the site's `Origin`; logout ends the session. WEB01's contract test can use the same lane. The page is `/` of the current Supabase-era site, which prints "The Supabase client could not start" in the dev-server output until WEB02 replaces the auth store: not a harness fault.
- Not done here: the dev server does not apply `vercel.json`, so the pending CSP-in-a-browser check of `tests/unit/hosting-headers.test.ts` needs a static server that does (WEB02 or later). `tests/e2e/login.spec.ts` (Supabase-era T-E01, T-E08) was removed because it ran on the Supabase global setup; it is in git at aca0f4a for WEB02 to port. `scripts/e2e-ports.cjs` (lane names and ports) is CommonJS on purpose: Playwright compiles what its TypeScript files import to CommonJS, which breaks `import.meta` and loses the named exports of an `.mjs` loaded twice.
- After a killed run: `LANE=b JV_API_DIR=... npm run e2e:lane -- down` (Ctrl-C during the start-up and during a test were both tried: the container is removed, no process or volume is left, and the next run cleans up first anyway). The API needs Node 24.7 by its `engines`; on this Mac's Node 22 it runs with the scrypt fallback (a login takes a few hundred ms).

## WEB01 API client: credentials, headers, Idempotency-Key, error map, waking-up retry, string money
- Use `import { api, ApiError } from '@/lib/api/client'` (one client per page load; its address is `NEXT_PUBLIC_API_URL`, read at the first call, an origin only, https except on localhost; `createApiClient({ baseUrl, fetch, sleep })` for tests). Calls: `api.get/post/put/patch/request`, the session calls `login/me/logout/activity/changePassword` (logout and activity send no body and no Content-Type) and the reads `syncPage(resource, {updatedAfter, afterKey, limit, signal})` and `poll(cursors, limit, {signal})`. Options of a call: `idempotent: true` for X1 to X12 except X7 (the key is made ONCE per call and kept through every retry), `readOnly: true` for a POST that saves nothing (poll, quote; the session calls are built that way: their failures never say "saved"), `idempotencyKey: error.idempotencyKey` when the person presses Save again for the same action (C6), `context: { customerId }`, `signal`. Each try is cut after 45 s (a cut try is NETWORK).
- Errors: `ApiError { code, status, details, requestId, idempotencyKey, message, nothingChanged, unconfirmed, retryAfterS }`; `message` is the plain text of C13 (a refusal before any write ends "Nothing was changed." on a write; JV_INVALID_INPUT and JV_NOT_ALLOWED show the API's own sentence); the client's own codes are `NETWORK` (no answer, never retried inside the client), `GATEWAY` (502/503/504 without an S8 body, or any reply that is not JSON, still there after retries at 1, 2, 4, 8, 15 s) and `BAD_RESPONSE`. JV_BUSY is retried once after its Retry-After (1 to 5 s). A code the client does not know is treated like JV_INTERNAL.
- Hooks (both return an unregister function): `api.onUnauthorized(fn)` runs on every 401 except JV_BAD_LOGIN (WEB02 registers the gate: empty memory, stop pollers, show login once; a 403 JV_FORBIDDEN is NOT a 401, the poller calls `me`); `api.onUnconfirmedSave(fn)` runs when a call that saves data ends unconfirmed (JV_INTERNAL, a second JV_BUSY, NETWORK, GATEWAY, BAD_RESPONSE) with `{ error, method, path, customerId }`: WEB07 registers the re-read of that customer's bill-summary and customer-balances (C13 says "bills and receipts", C17 says "bill_summary rows and the customer_balances row": the hook gives only the customer, the screen decides).
- Banner (C7): `api.getConnectionStatus()` / `subscribeConnection(fn)` give 'ok' | 'waking' | 'offline' (shape for `useSyncExternalStore`), `CONNECTION_BANNER` holds the words; any answer from the API clears it except JV_UNAVAILABLE (offline). Disable every Save control while it is not 'ok'. Polling: `nextPollDelayMs(failures)` is 8 s, then 8, 16, 30 s after failures; the poller owns the loop and passes a `signal` to stop on logout.
- Pricing (C12): `api.me()` fills `getPricingCheck()`; `savingBillsAllowed()` is false before `me` has answered, on a mismatch and when the API sends `null`: WEB07 disables Save on bills and shows the banner. The build's own hash is `src/lib/api/pricingHash.ts`, generated from the bytes of `src/lib/pricing.ts` by `scripts/pricing-hash.mjs` (`npm run pricing:hash`; `npm run build` runs it first; `npm test` fails when the file is stale). A new pricing.ts goes to the API repository with its new hash in `PRICING_SHA256` (loginRoutes.ts) and PRICING-SOURCE.txt.
- Money and weight (S3): a JS number under a name of `WIRE_TEXT_FIELDS` (amount, metal_rate, piroi, discount, grams, gross_weight ... both the DECIMAL columns and the derived figures) in a request is a TypeError before any call, a fraction or NaN anywhere is too, and the same number in an answer is `BAD_RESPONSE`; `settings.value`, `details`, `old_row`, `new_row` are not looked into. A function that brings a new money or weight field name must add it to that list. `types.ts` follows the built API (handoffs API05, API11, API18) where NODE-DESIGN differs: `server_time` on every sync page, `updated_at` on users rows, booleans for flags, `item_count` a number; the X1 to X12 answer shapes are the design's and not yet checked against a built route.
- Contract test: `E2E=1 LANE=b JV_API_DIR=... npx playwright test tests/e2e/api-client.spec.ts` runs the real `client.ts` (transpiled by the test and served at /__jv/ on the site's origin) in Chromium: login, me (hash equals the build's), activity, keyset paging of settings, customers, a poll, JV_BAD_LOGIN (no hook), JV_INVALID_INPUT from a wrong current password (422 on `current_password`), a 401 after logout (hook once), JV_FORBIDDEN of a staff poll, and the CORS preflight of `Idempotency-Key`. WEB07's forced-retry test can copy its `openClient`/`call` helpers. The page must be a document the dev server sent (its 404 page): a page the test fulfils itself has no address space and Chromium blocks its call to the loopback API ("Local Network Access").
- Not touched on purpose: `src/lib/authStore.ts` (WEB02 rewrites it and registers the 401 hook) and the Supabase files (WEB15).

## WEB03 Hydrate behind the loading gate, merge by id (stock side first)
- The memory is `rowCache` (`@/lib/cache/cache`): rows by resource and key, `merge(resource, rows)` keeps the copy with the greater `updated_at` (microsecond numbers parsed from the exact text by `@/lib/cache/stamp`; an equal stamp lets the later copy in), `get`, `rows` (the same array until the resource changes), `versionOf(...resources)` (views are cached by it), `subscribe`, `clear`. WEB04 merges every poll answer with `rowCache.merge`; a row it cannot key or order throws `CacheDataError` (show the plain "could not load" error, never the row). Nothing is ever put in browser storage.
- The loader is `hydrator` (`@/lib/cache/hydrate`; `getHydrateState()`, `useHydrate()`, `startHydrate(role, epoch)`, `retryHydrate()`): `resourcesFor(role)` is the table of A4 (owner 15, biller 14 without sku-private, staff 7; a Playwright case checks it against the real API for each role), stock side first, 3 tables in flight, pages of 1,000 that follow the server's `next` (so a cap of 500 works; a cursor that does not move is an error). A failed page empties what had arrived and shows the plain message with "Try again" (a 403 asks `reviewRole()` once first). To hydrate again (`data_epoch` changed): `hydrator.reset()` then `hydrator.start(role, epoch)`.
- FOR WEB04: `getHydrateState().pollFrom` is the first poll's cursor: the earliest `server_time` of the hydrate's first pages minus 30 s as exact six-decimal text (`stampMinusSeconds`), set only when `status` is 'ready'; start the poller only then, and register your own `registerLogoutHook` for it (the cache's hook is `bindToSession`, already registered once). `AppLayout` keys the data gate on `isGateOpen(state, role, epoch)`, so a new epoch shows the gate again until its own load is whole.
- The stock-side stores (`designStore`, `catalogStore`, `settingsStore`) keep their exports and read the cache: views are cached by `versionOf`, so `getDesigns()` is the same array until a design, piece, category, sub-category, user or sku-private row changes. Weights and amounts there are JS numbers made from the API's text, for display only; money is worked out from the cache rows' text (WEB07, WEB08), never from them. Every WRITING function (`addDesign`, `updateSkuStatus`, `addCategory`, `saveSettings` ...) throws `savingNotAvailable(...)` ("... cannot be saved yet") in a real build until WEB05, WEB06 and WEB08 put it on the API; a preview build (`src/lib/previewMode.ts`, re-exported by authStore) keeps the prototype's local behaviour and its sample data.
- The rates in `getSettings().estimate.defaultGoldRate/SilverRate` are the latest-dated `daily-rates` row of the material (0 when none: no sample rate), an interim for the rate card until WEB05; staff, who read 7 settings keys, get the app's own labels for `business`, `estimate` and `taxes`. Designs show the placeholder image (photos are WEB06).
- The money-side store `appStore` is NOT on the cache yet (WEB07): it holds nothing in a real build (it reads no sample customer and no `jaishri.*` key, and writes none); the cache already holds customers, bills, bill-summary, bill-items, receipts, receipt-allocations and customer-balances for the owner and the biller. Left alone, outside this task: `design-detail/page.tsx`, `DesignAuditLog.tsx`, `DesignSalesHistory.tsx` and `ScanDetailClient.tsx` still hold hard-coded sample text (SET-00572 ...), `DesignSkuTable.tsx` has a simulated `USER_ROLE = 'admin'` that offers the owner-only weight toggle to every role (the weight is absent for them: the cells show a dash), and `orderStore.ts` (a hidden screen) still uses `jaishri.orders.v1`. - Tests: `tests/unit/cache.test.ts`, `hydrate.test.ts`, `stock-stores.test.ts` (T-E05, T-F03, T-E01 clauses), `memory-reads.test.ts` (C9: the 16 files with a timer make no network call), `tests/e2e/hydrate.spec.ts` (12 cases, about 1 min). ## WEB04 Polling, merge, offline banner and 'Waking up' (poller, pending hold, SaveButton)
- The poller (`@/lib/cache/poll`, started by importing it: AppLayout does) sends one `POST /v1/sync/poll` every 8 s (`clampPollIntervalMs`: 5 to 10), at once after any write (the client's new `api.onWriteFinished(hook)` fires when a call that saves is over, success or not: WEB05 and later call nothing), every 30 s in a hidden tab and at once when shown or when the browser says `online`, and 8, 16, 30 s apart while polls fail. The cursor of a resource is the greatest `updated_at` received minus 30 s (six decimals, no key); the first poll uses `getHydrateState().pollFrom`; rows are merged only when every page of the poll has arrived. `pollNow()`, `usePollState()` (`failures`, `notice`, `polls`), `createPoller({...})` for tests (`tests/unit/support/server.ts` is a fake server for the REAL client over `fetch`, on the clock the fake timers move).
- Ordinary edits (WEB05): `const release = rowCache.hold(resource, key)` before the optimistic merge, `release()` when the write has ended (after merging the returned row, or the rollback). A poll's copy of a held row (`merge(..., { polled: true })`) waits aside and is let in at the release only if it is newer than what memory holds; your own `merge` calls are never held back. A logout drops all holds.
- Save controls (C7): `SaveButton` (`@/components/ui/SaveButton`, a drop-in `<button>`, disabled while "Offline: changes cannot be saved" or "Waking up…" shows, the banner words as its title) and `useSavingAllowed()` (`@/lib/api/connection`) are the one mechanism; every control that saves uses one of them. Only the rate card's "Save Rates" (the one Save control a real build shows on the first page) uses it so far. The other prototype Save buttons (SettingsClient x6, EditStockClient, AddDesignClient, CustomerSearchPanel, BillingSummaryPanel, ReceivePaymentPanel, CustomerLedgerClient, hidden OrderBookClient and the estimate edit mode) are NOT converted on purpose: `npm run lint:changed` lints every file changed since main, and those files carry React-compiler errors of their own ("impure function during render", "setState in an effect"; none of them is touched by this task), so the task that rewrites each screen (WEB05 to WEB09) swaps `<button>` for `<SaveButton>` then; in a real build their store calls throw `savingNotAvailable` until then. The banner is `ConnectionBanner` at the top of AppLayout (`data-testid="connection-banner"`, `data-state`); a poll that fails for another reason shows one strip ("The latest changes could not be loaded. <reason>", `data-testid="poll-notice"`) that clears with the next good poll.
- `data_epoch` is the settings row of that name (the poll answer has no epoch field): when its value changes the poller runs `hydrator.reset()` then `start(role, epoch)` and the gate shows again. A poll answer whose `role` is not the session's, and a 403, call `reviewRole()` once; a 403 with the same role shows the notice and backs off and `me` is not asked again until a poll works. No audit data is in memory yet: WEB10's store must `registerLogoutHook` to be emptied by a demotion (a unit test proves a stand-in is). The poll interval is a constant, not a `settings` row (D3 lists no such key).
- Tests: `tests/unit/poll.test.ts` (44), `cache-pending.test.ts` (10), `connection.test.ts` (7); `E2E=1 npx playwright test tests/e2e/poll.spec.ts` (13 tests and 2 `test.fixme`, about 6 min; rows are written as root in the lane's container: designs, pieces, a bill of the walk-in, 20 s and 40 s transactions, one held open from the test). The money halves (a payment moves the other browser's pending and balance, cancelling an unpaid bill, a money call retried with the same key) are `test.fixme` until WEB07 and WEB09; the unit tests already prove that touched bill-summary and customer-balances rows reach memory. `tests/e2e/login.spec.ts` T-D06 (WEB02) now holds the polls with `page.route`, because the 8-second poll meets a deactivated user's 401 before the test's click does; the poll path of that is in poll.spec.ts.
