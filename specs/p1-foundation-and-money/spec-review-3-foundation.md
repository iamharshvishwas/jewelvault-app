## 2. The three claims, re-run (Supabase image as role `postgres`; PostgREST where the claim is about the Data API)
- **A3 recipe.** Before it, anon and authenticated could run `public.old_fn`, read `public.old_tbl`, use `old_seq` and held EXECUTE on `private.old_fn` (no schema usage yet). After the recipe as worded: all existing objects false for both; `private.app_role()` and schema `private` usable by authenticated only; objects made later by `postgres`: `public` function, table, sequence, view false for anon and authenticated, true for `service_role` ("keeps its default access"); `private` ones false for all. As real roles: authenticated got "permission denied" on a later private function and on `public.new_tbl`, anon on schema `private`. A1's event trigger, created by `postgres`, put RLS on tables made by `CREATE TABLE`, `CREATE TABLE AS` and `LIKE` in both schemas. Residue: the image also grants to anon and authenticated for objects `supabase_admin` makes in `public` (a platform tool or an extension install); a table and a function made that way after the recipe were still reachable. A3 can only revoke `for role postgres`, so T-D02's catalogue check on the dev project is the guard. TRUE.
- **S4 literals + D7 trigger.** Literal `CHECK` caps plus an invoker trigger with no EXECUTE for authenticated: an edit within the rules worked; gross below NW, NW 0 on By Weight refused; NW 0 on Per Piece accepted. A `CHECK` calling a private function failed every update with "permission denied for function" (S4's "tested" holds). T-F02's comparison works: `pg_get_constraintdef` gives `(customer_net_weight <= (100000)::numeric)`, one regex reads 100000. TRUE, with RF3-2 and RF3-3.
- **Timeouts and hook.** Function clause `SET lock_timeout = '1s'` cut the idempotency insert's wait for an in-flight twin after 1.4 s and raised `JV_BUSY`; a `set local` after the first statement waited 3.3 s (X0.7's "too late" is right); the setting is restored on exit. Through PostgREST a request as authenticated sees `statement_timeout=8s lock_timeout=8s`; with the role set to 500 ms (`notify pgrst, 'reload config'`) a 1.5 s call is cancelled at 0.5 s, and a `set local statement_timeout` inside a function at the default 8 s changes nothing (C4's sentence). Hook: while A paused (`Lock/advisory`), B waited behind A's row lock (`Lock/transactionid`); both applied (balance 2). TRUE, with RF3-7 and the T-C15 note in RF3-5.

## 3. New findings (changed lines only)
**RF3-1 | Medium | C3 l.213, H3 l.247, DB21 | The empty-page rule does not stop a lowered `max_rows` losing rows; it only stops the load ending early**
- PostgREST with `max_rows=500`, 2,500 rows: `Range: 0-999` came back `0-499`; C3 does not say how `from` advances; the natural loop (next page at +1,000, stop on an empty page) loaded 1,500 distinct rows in 4 requests and missed 1,000 without an error; advancing by the rows received loaded 2,500 in 6. H3 reads the repository's `config.toml`; DB21 never reads the hosted Max Rows.
- Fix: C3 advances by the rows received (or checks the total); DB21 reads the hosted `max_rows`; T-F03 gets a `max_rows = 500` case. FE03 and FE04b repeat the wording. Kind: small defect.

**RF3-2 | Medium | D7 l.120, O37 | The weight trigger treats a blank gross weight as a real zero, and fires on status-only updates**

- Fix: check NW ≤ gross only when gross is above 0 and only when a weight or the design changes (`UPDATE OF`); ask Siddhi if she records gross (O37). Kind: visible-behaviour choice for Siddhi plus a small defect.
