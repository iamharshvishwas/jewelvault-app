**RF-1 | Medium | D23 l.142, C3 l.213, C4 l.214, V2 l.363 | A cancelled bill with no payment never moves the customer's `updated_at`, so other terminals keep the old balance**
- Wrong: D23 touches the customer on "an insert or update on `receipts` or `receipt_allocations`" and "an insert on `bills`". `cancel_bill` (K3, X5) updates the bill and releases allocations; with nothing allocated there is no allocation row, so no touch. V2 `billed`, `outstanding`, `balance`, `last_purchase` and the ledger change, but `customer_balances.updated_at`, which C3/C4 rely on ("reloaded when that customer's `updated_at` changes"), does not. A mistaken bill cancelled before any payment is probably the commonest cancel.
- Effect: the second terminal and the owner's dashboard show the old outstanding until another payment touches that customer or the page reloads. Also V2 lists no `id`, while C3/C4 order and merge by `id`.
- Fix: add `AFTER UPDATE OF status ON bills` to the touch list (customer and bill); give V2 an `id`; T-E07 case "cancel an unpaid bill, the other browser's outstanding changes within 10 s". Kind: small defect.

**RF-2 | Medium | C4 l.214, X0 item 7 l.341, S8 l.99, IM1 l.253 | The "30-second overlap" argument fails for the import, and the timeout meant to guarantee it does not work as written**
- (a) C4: "Every function sets `lock_timeout = '5s'` and `statement_timeout = '15s'`, so no transaction stays open long enough to commit a row older than the overlap". IM1 runs "one transaction per batch" on the owner's connection; rows are stamped when written, committed minutes later. Exp 3 (8-second writers, C4's cursor rule): a row stamped at t=0 and committed at t=40 s was never returned (cursor 43.4 s newer); it exists, and only a reload shows it. Terminals open during an import miss stock, customers and bills for good.
- (b) Exp 1 (PostgreSQL 17.11, simple and extended protocol): `set local statement_timeout = '300ms'` inside a function, and a function-level SET clause, did not cut a 1.5 s call (1,510 ms); a top-level SET did. `lock_timeout` set inside does work (cut at 513 ms). Supabase's timeouts page says a function-level setting works through the REST API (I could not reproduce that on stock PostgreSQL) and gives role defaults of 8 s for authenticated, 3 s anon, postgres capped at 2 minutes, changed by `ALTER ROLE ... SET` plus `NOTIFY pgrst, 'reload config'`. So the bound the tests will meet is 8 s, not 15 s.
- Fix: (a) the import's last statement before COMMIT re-stamps `updated_at = clock_timestamp()` on the batch's rows, batches stay under 20 s, and either "no terminal open during an import" or a `settings` row `data_epoch` that makes open screens re-hydrate; T-E07 gets a 40-second writer case (expected: delivered). (b) State the role setting (`ALTER ROLE authenticated SET statement_timeout`) or accept 8 s; keep `lock_timeout`; T-C15 tests it on the real stack. Kind: small defect; (a) has a choice of mechanism for the plan.

**RF-3 | Medium | A3 (1) l.148, A1 l.146, T-D02 l.542, T-D16 l.556 | The default-privilege revoke it cites leaves EXECUTE on later functions with PUBLIC, so with anon and authenticated**
- Wrong: A3 (1) revokes for functions "created later in `public` and `private`, from `public`, `anon` and `authenticated` (the SQL is on the securing-your-api page)". That page's four statements are all written `for role postgres in schema public`, including `revoke execute on functions from public`. PostgreSQL's ALTER DEFAULT PRIVILEGES page says of that statement: "This command has no effect, unless it is undoing a matching GRANT" (per-schema defaults only add to the global ones). Exp 2 (fresh database, Supabase-like default ACL): after those four statements, and the same for `private`, a new function in `public` and one in `private` were still executable by anon and authenticated (tables were not); after `ALTER DEFAULT PRIVILEGES FOR ROLE postgres REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` (no IN SCHEMA) neither was. The ledger spike ("a new function reaches anon") shows the same exposure, and A3 as worded would not remove it. A3 (2) has the same gap for functions that already exist: `revoke all on all functions in schema public from anon, authenticated` left an existing function executable by both (Exp 2b) until it was also revoked `from public`; A3 (3) does say `public` for `private`.
- Effect: `authenticated` has USAGE on `private` (A3 (3)), so any later private function is executable by every signed-in user (not reachable through the Data API, but A3's layer is gone); later public functions are protected only by A6's hand revoke. T-D02/T-D16 "later objects are not granted" would fail on functions. The page's event-trigger example covers `public` only, A1 says `public` and `private`.
- Fix: A3 (1) names the global form; A3 (2) adds `from public` for functions; in-schema revokes stay for tables and sequences; the event trigger covers `private`. Kind: small defect.

**RF-4 | Medium | S4 l.95, D18 l.137, A3 (3) l.148, D2 l.112, T-D16 l.556 | "The caps live in one place (`private.limits`)" cannot be a CHECK that calls a private function: direct stock edits would fail**
- Wrong: a CHECK cannot read a table, so "one place" means a private function called by the CHECKs. Exp 4: a CHECK calling a private function the writing role cannot EXECUTE made every UPDATE of that row fail with "permission denied for function", even an update of another column. A3/T-D16 leave `authenticated` only `private.app_role()`, so the first staff edit of a weight (T-C07, T-D04) fails. - Fix: the caps are literals in the CHECKs, generated from one migration file (functions read `private.limits`); or grant EXECUTE on one named helper and list it in T-D16. Kind: small defect (two rules that cannot both hold).

Kind: text is a small defect; the organisation/cost point is Harsh's (O19).

## Experiments (stock PostgreSQL 17.11 in jv-rev2-pg; SQL abbreviated, outputs as printed)
- Exp 1 (timeouts): `create function t() ... begin set local statement_timeout = '300ms'; perform pg_sleep(1.5); return 'finished'; end;` then `select t();` returned after 1,510 ms (1,511 ms with `\bind`, i.e. the extended protocol; 1,514 ms with `SET statement_timeout` as a function clause). `begin; set local statement_timeout = '300ms'; select pg_sleep(1.5);` gave `ERROR: canceling statement due to statement timeout`. A function doing `set local lock_timeout = '500ms'` and then updating a row held by another session raised `lock_not_available` after 513 ms.
- Exp 2 (default privileges, fresh database): default ACL for role postgres in schema public granted to anon, authenticated, service_role; then the page's four statements (all `in schema public`, the last `revoke execute on functions from public`) and the same for `private`; created `public.f1()`, `private.g1()`, `public.t1`. Result: `public.f1 anon/auth exec = true/true ; private.g1 = true/true ; public.t1 select = false/false`. After `alter default privileges for role postgres revoke execute on functions from public;` new `f2`, `g2`: `false/false ; false/false`. Exp 2b (fresh database): existing `public.f_existing()` was executable by anon before and after `revoke all on all functions in schema public from anon, authenticated`; only `... from public` closed it.
- Exp 3 (polling): table with `updated_at default clock_timestamp()`; session A: `begin; insert id 1; select pg_sleep(40); commit;` session B inserts a row every 8 s and polls `updated_at >= cursor - 30 s` (cursor = greatest `updated_at` seen). Polls at t+1, 9, 17, 25, 33, 41 s saw {2}, {2,3}, {2..4}, {2..5}, {2..6}, {3..7}; after A committed the next poll saw {4,5,6,7}; row 1 is in the table, stamped 43.4 s before the cursor.
- Exp 4 (CHECK): `private.max_weight()` with EXECUTE revoked from authenticated; `check (nw <= private.max_weight())`; column grant `update (nw, note)`; as authenticated both `update ... set nw = 20` and `update ... set note = 'b'` gave `ERROR: permission denied for function max_weight`.
- Exp 5 (profiles): trigger on a stub `auth.users` inserting `profiles(full_name text not null)` from `raw_user_meta_data->>'full_name'`; `insert into auth.users(email)` gave `null value in column "full_name" ... violates not-null constraint`, `users_created = 0`. A BEFORE UPDATE guard (`old.id = auth.uid()` and role/active changed): own role gave `JV_FORBIDDEN`, own `full_name` and another profile's role were allowed.
- Exp 6 (grants): trigger function in `private` with EXECUTE revoked still fired for authenticated and moved `updated_at`; `update ... set status` (no column grant) gave `permission denied for table`; `update ... where updated_at = '<text as returned>'` changed 1 row, the same statement again 0 rows.
- Exp 7 (L5): `insert ... on conflict do nothing` in session A (kept open 3 s) and the same in B: B waited about 3 s, inserted 0 rows and read A's stored result `{"bill": "JV-2026-0001"}`; with A rolled back, B inserted 1 row.
- Exp 8 (matrix): a mini model of A3/A4/A5 (global default revoke, `private.app_role()`, one policy per table and command, column grants, the A5/A8 triggers) probed by 39 statements as owner, biller, staff, an inactive user and anon. Everything matched A4 except that a biller could insert `daily_rates` dated yesterday and tomorrow (RF-11); RLS-denied updates return 0 rows, not an error; staff changing `designs.material` to a new value gave `JV_FORBIDDEN`; anon got `permission denied` for tables and for schema `private`.
